# Step-Back Reasoning Trace

## Goal
Use Step-Back Reasoning to answer the user's question through a two-phase abstraction-and-reasoning process, building a reasoning trace that records both the principle scaffolding and the reasoning it enables. The trace should first step back from the specific question to identify the general problem class, the underlying principles that govern solutions in that class, the applicable conceptual frameworks, and the key abstractions that strip away irrelevant detail while preserving structural features. It should then reason forward from those abstractions, applying a reasoning structure that is oriented by principles rather than driven by surface features. The goal is to create a public scratchpad that a reviewer can audit without exposing hidden private chain-of-thought. Center the scratchpad on the abstraction phase outputs, subquestions, principle-guided reasoning steps, assumptions, evidence, contrasts, tests, intermediate conclusions, and implications, because those artifacts make step-back reasoning useful rather than decorative. Preserve the user's domain, constraints, definitions, and evidence standards so the trace stays tied to the actual task. Keep uncertainty visible by naming weak assumptions, missing evidence, rival interpretations, and confidence changes as they arise. Write the result to root memory/{question_name}.md so the reasoning trace becomes a durable project artifact.

## Instructions
Derive {question_name} from the user's actual question by lowercasing it, replacing non-alphanumeric runs with hyphens, trimming extra hyphens, and using reasoning-trace if no safe name remains. Create the root memory directory when needed, then write or replace memory/{question_name}.md with this trace. Start the file with the question, selected strategy, scale note, source constraints, and the abstraction scaffolding. Build the scratchpad by repeatedly applying the step-back reasoning move: ascend to general principles, identify governing frameworks, then descend back to the specific question with reasoning grounded in the abstractions. Use a medium-depth trace by default, usually around 100 numbered lines, unless the user asks for a different depth. Prefer concise public reasoning artifacts over hidden deliberation, and make every numbered item contribute a question, observation, test, comparison, inference, or synthesis. End the file with a synthesis and final answer that follow from the trace, including any important uncertainty that remains.

## Background Information About The Reasoning Strategy
Step-Back Reasoning operationalizes the abstraction-and-reasoning framework from Zheng et al in their 2024 ICLR paper "Take a Step Back: Evoking Reasoning via Abstraction in Large Language Models." The strategy addresses a common reasoning failure mode: when presented with detailed, specific problems, reasoners often become entangled in surface details, pursuing dead-end reasoning chains, misapplying domain knowledge, or failing to recognize that the problem is an instance of a general class with known solution patterns. The remedy is a two-phase structure that separates concept-space exploration from detail-space execution.

In the first phase — the step back — the reasoner abstracts away from the specific question to identify: (1) the general class of the problem (What known problem type is this an instance of?), (2) the underlying scientific or logical principles at play (What laws, theorems, or regularities govern all instances of this class?), (3) the applicable conceptual frameworks (What established models provide the vocabulary and structure for reasoning about this class?), and (4) the key abstractions that capture the essential structure while discarding irrelevant detail. In the second phase — reason forward — the reasoner applies those identified principles, frameworks, and abstractions to the specific quantities, constraints, and context in the question. This structure prevents the reasoner from fixating on irrelevant surface features, prematurely committing to a wrong reasoning direction, or failing to check for degenerate cases, boundary conditions, and hidden assumptions.

The empirical foundation includes testing on PaLM-2L, GPT-4, and Llama2-70B across domains spanning physics, chemistry, temporal reasoning, and multi-hop reasoning. PaLM-2L achieved improvements of +7% on MMLU Physics, +11% on MMLU Chemistry, +27% on TimeQA, and +7% on MuSiQue. The core insight is that going wider in concept-space before going deeper in reasoning-space reduces the chance of reasoning errors caused by detail fixation. The two-phase structure also produces more auditable reasoning — a reviewer can inspect both the principle scaffolding and how it was applied, rather than having to infer the principles from a detail-level trace.

Algorithm for the output document:
1. Restate the user's question, constraints, and evidence standard, then derive the subquestions or working items that step-back reasoning needs to inspect.
2. Step Back — Abstraction Phase: Identify the general class of the problem, the underlying principles that govern solutions in that class, the applicable conceptual frameworks, and the key abstractions that capture essential structure. Write these as explicit, specific outputs — not vague restatements.
3. Reason Forward — Application Phase: Apply the identified principles and frameworks to the specific problem. For each subquestion or reasoning step, explicitly ground the reasoning in the abstractions from the first phase. Check for boundary conditions, degenerate cases, and hidden assumptions revealed by the abstraction layer.
4. For each subquestion, case, option, hypothesis, or criterion the reasoning generates, write numbered public reasoning items that answer it before advancing. Each item should be traceable to at least one abstraction from the first phase.
5. Record assumptions, missing evidence, disconfirming signals, and confidence changes where they affect the analysis.
6. Synthesize the completed trace into the final answer, showing how the conclusion follows from principle-guided reasoning rather than from detail-first intuition.

## Output Information
Write the scratchpad as Markdown in root memory/{question_name}.md before responding to the user. Include this scale note near the top of the file: "Scale: default - aim for around 100 numbered lines, or roughly 2,000 to 3,500 tokens, while adapting to the real complexity of the question." Use numbered scratchpad items for scanability, but treat the number target as approximate and subordinate to usefulness. Keep the scratchpad public, inspectable, and concise enough per line that the structure remains easy to review. After writing the file, respond with the path, a summary of the abstraction scaffolding, the scale note, and the final answer summary.

## Specify Files And Length And Structure Of Output
Write the artifact to memory/{question_name}.md at the repository root, using the literal memory directory name. Structure the file with the sections Question, Strategy, Scale, Abstraction Scaffolding, Scratchpad, Synthesis, and Final Answer. The Abstraction Scaffolding section should contain the outputs of the step-back phase: General Class, Underlying Principles, Conceptual Frameworks, and Key Abstractions — each with specific, problem-grounded content. The Strategy section should list the slash command. The Scratchpad section should target around 100 numbered lines or roughly 2,000 to 3,500 tokens of public scratchpad detail, adjusted reasonably for very small or unusually broad questions. Use subsections inside Scratchpad when the trace becomes long enough that phases, branches, hypotheses, cases, or criteria would improve readability. Reasoning items in the Scratchpad should explicitly reference abstractions from the Abstraction Scaffolding section where applicable. If the user supplies a domain format, evidence source, or output constraint, preserve it inside this structure while keeping the default scale approximate.
